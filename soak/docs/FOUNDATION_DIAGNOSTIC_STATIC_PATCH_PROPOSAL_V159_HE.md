# v159 — הצעת קוד אבחון נפרדת למקורות Ada ו־Python, ללא הרצת מקור

## הבעיה שהצעת האבחון אמורה לפתור

Issue #29 מתעד שבאותם קלטים `F(c=-15055671,t=-15055671)` נצפה פלט מקורי שונה: `[5000,10,503,30,52]` ב־Ada לעומת `[5000,10,503,20,56]` במקורות Python/TypeScript/Fortran. קיים פער ידוע במרחב שזרות החודשים ובשיטת בחירת הרנק (v110 ו־v139–v141), אך מקור הפער המספרי הספציפי אינו מבודד. מתוך הפלט הסופי אין להסיק את מזהה החודש הפנימי או את שיוך שמות החודשים (v157).

ב־v158 הותקן מנגנון קבלות סינתטיות בלבד. **v159 מתקדם שלב אחד לכיוון אימות אמיתי:** הוא מכין מראש קובצי מקור עם נקודות אבחון מדויקות, להשוואה ולסקירה, מבלי לקמפל אותם ומבלי להריץ פונקציות תאריך.

## מבנה החבילה

הסקריפט `soak/runner/soak_foundation_diagnostic_patchplan_v159.py` קורא שלושה קובצי מקור היסטוריים — שניים שיש להכין מהם הצעות ואחד המשמש נעילת מקור של Ada — ומאמת תחילה כל Git blob SHA-1 מול קומיט מקובע:

| מנוע | קומיט היסטורי | קובץ |
|---|---|---|
| Python+Türkçe | `0e4e75886dea4f4c7e0b6e39cce79e1d66f046f4` | `tests/normative_reference.py` |
| Ada+తెలుగు | `a2fb6811ce8c1c4aa3e2d0dffc9f2ea549803b72` | `src/normative_oracle.adb` |
| Ada+తెలుగు — נעילת שזירה | אותו קומיט | `src/month_weaving.adb` |

לאחר אימות המקורות נוצרים תחת ספריית פלט חדשה בלבד:

- `instrumented_normative_reference_v159.py` — עותק Python עם שתי נקודות תיעוד.
- `instrumented_normative_oracle_v159.adb` — עותק Ada עם שלוש נקודות תיעוד.
- `REF_41.diff` ו־`ADA_TELUGU.diff` — שינויי שורות מאוחדים לקריאה ביקורתית.
- `manifest.json` — מזהי המקור, SHA-256/Git blob של הקובץ ההיסטורי ושל עותק ה־QA, וסימון מפורש שאין כאן הרצת מקור או הוכחת שקילות סמנטית.

**מנגנון סירוב:** אם נעילת המקור נכשלה או שמחרוזת היעד לשינוי חסרה/מופיעה יותר מפעם אחת, אין הכנת עותק. ההוספה כוללת סמני פתיחה וסגירה ייחודיים. הסרת מקטעי ההוספה בלבד חייבת לשחזר **את כל בתי הקובץ המקורי**, כולל סיומות שורה. מכך מוסקת רק היכולת להפוך את שינוי הטקסט, לא שקילות התנהגותית.

קובץ Python המותאם עובר `ast.parse` לצורך בדיקת תחביר בלבד, **בלי import, בלי compile של ממיר מקורי ובלי `F(c,t)`**. לגבי Ada מבוצעת בדיקת עיגון טקסטואלי והפיכות בלבד; **תקינות התחביר ויכולת הקומפילציה של העותק אינן נבדקות**. אין להסיק אחרת גם אם מבחני Python עברו.

## נקודות התיעוד המוצעות

ב־Python, לפני `return family.unrank1(rank)`, כשהבחירה כבר נעשתה, הצעת הקוד מתעדת את `month_lengths`, גודל המשפחה ו־`global_rank`. לפני `return DateIds(...)` מתועדים גבולות השנה, `month_count`, וקטור אורכי החודשים, רצף שזירת החודשים, מערך השמות הקנוניים, אינדקס היום בתוך השנה, מזהה החודש הפנימי, יום־בחודש ו־`month_index`.

ב־Ada, לאחר קביעת רנק אורכי החודשים, מוצעת רשומה עם הרנק המקורי; לאחר יצירת `Tickets` מתועדים כל הכרטיסים לפי סדרם; ובשלב `calendar_result_ready` מתועדים גבולות השנה, קלטי תאריך, מספר החודשים, `Month_Rank`, `Month_Name_Rank`, וקטור אורכי החודשים, רצף השזירה, מערך השמות, מזהה החודש הפנימי ויום־בחודש.

בשתי השפות התיעוד המוצע מופרד מ־stdout הרגיל ונכתב ל־**stderr** רק כאשר `PC_FOUNDATION_DIAG_V159=1`. זה מקטין את הסיכון לערבוב פלט תאריך עם דיאגנוסטיקה, אך אינו מהווה הוכחה שהקוד המותאם יתנהג בדיוק כמו המקור.

## מגבלות מדעיות ובקרות נוספות

1. **העותקים המותאמים אינם מקורות היסטוריים**: אפילו אם הפונקציות המתמטיות לא שונו במתכוון, שינויי לוגיקה אפשריים בשל הדפסה, שגיאות I/O, שימוש נוסף בזיכרון או תזמון. אין להציג את תוצאתם בתור תוצאה של אותם בתים היסטוריים.
2. **אין קומפילציה של Ada**: ייתכנו שגיאות תחביר, טיפוס, נגישות שם או בעיות סביבת הרצה שאינן מזוהות בבדיקה סטטית. יש לוודא זאת בנפרד ובהרשאה מתאימה לפני שימוש.
3. **אין אותנטיקציה של פלט**: הדפסת ערכי ביניים על stderr אינה מספיקה לבדה להוכחת מקור. במקרה של שימוש עתידי נדרשת גם קבלה חיצונית של תהליך OS, גיבובי קבצים, בינארי, ארגומנטים, stdout/stderr גולמיים והפקדת ארטיפקטי CI. v158 הוא פורמט קבלות סינתטי ואינו תחליף לזה.
4. **אין ייחוס סיבה בלעדית**: רשומות ביניים אמיתיות עשויות להראות יותר מנקודת פיצול אחת או את השפעתה של תלות משותפת ב־`Sauce`. כל טענה על נקודת כשל ראשונה חייבת להתבסס על השוואת שדות שנצפו בפועל.
5. **אין הרשאת הרצה ב־v159**: עצם הכנת קובצי אבחון אינה מבטלת את `STOP_NEW_NATIVE_SOAK_DISPATCH`. להפעלת כל עותק מותאם, גם על יום בודד, נדרשת הכרעה מפורשת ומתועדת ב־Issue #29 ובקרות משאבים וסביבת ריצה בהתאם.

## אמות מידה לקבלת שלב הכנת הקבצים

CI חייב להראות 30/30 בדיקות v159, נוסף ל־60/60 בדיקות v157–v158, שלוש נעילות Git blob, יצירת שני קובצי הצעה שונים מן המקור, יצירת קובצי diff וקובץ manifest, בדיקת AST של Python, והשוואה מדויקת לבתי המקור לאחר הסרת ההוספות. יש לאמת גם את מצב `Issue #29 OPEN`, `main` ללא שינוי, **0 קריאות `F(c,t)` חדשות, 0 קומפילציות מקוריות ו־0/10,000 שנות מקור מאושרות**.

בכל מקרה, קבלה של הכנת המקורות אינה קבלה של קוד אבחון בר־הרצה, ואינה אישור לעקוף את החסימה.
