# اختبار عرض العربية في الطرفية — Stage 49

الحالة: **إجراء تحقق يدوي لم يُنفَّذ بعد**. لا يمثل نجاح اختبارات Unicode/UTF-8 أو نجاح CI تصريحًا بنجاح العرض المرئي أو إمكانية الوصول. لا يشمل هذا الإجراء واجهة رسومية للمنتج؛ المشروع مكتبة، ويُستخدم برنامج اختبارات Stage49 بوصفه مسبارًا لطرفية فعلية.

## التنفيذ

المتطلبات: .NET SDK 10، وطرفية فعلية تدعم UTF-8 والخط العربي. شغّل من جذر المستودع، على الفرع `C#+العربية-الفصحى` وبـ HEAD موثَّق:

```sh
dotnet run --project tests/PastafarianCalendar.Stage49Tests/PastafarianCalendar.Stage49Tests.csproj -c Release -- --visual-rtl
```

الوسيط `--visual-rtl` **اختياري**؛ المسار المعتاد من دون الوسيط لا يتغيّر. سيطبع المسبار ثلاث رسائل عربية حقيقية مأخوذة من الاستثناءات التي يفحصها Stage49 بالفعل، مسبوقة بعلامة `STAGE49_ARABIC_TERMINAL_QA_BEGIN` ومتبوعة بعلامة `STAGE49_ARABIC_TERMINAL_QA_END`. الأرقام اللاتينية والعربية والرموز بين الأقواس في هذه الأسطر **مقاطع اختبار للعرض فقط**، وليست رسائل إنتاج جديدة.

## ما يجب ملاحظته وتوثيقه

1. ترتيب الأسطر المرقّمة ١، ٢، ٣، والاتصال الصحيح للحروف العربية وعدم ظهور بديل U+FFFD أو مربعات الخط أو حروف معكوسة.
2. ظهور الأعداد `123 / ١٢٣`، `456 / ٤٥٦`، `789 / ٧٨٩`، والأقواس `[A-1]` و`(B:2)` وما يماثلها، ضمن السياق الصحيح دون اقتطاع أو تبديل غير مفهوم عند حدود اتجاه النص.
3. مقارنة النسخ من الطرفية بالنص المنطقي الأصلي؛ قد تختلف المواقع *المرئية* باختلاف تطبيق خوارزمية Unicode BiDi، ولذلك لا يكفي فحص سلسلة البايتات لإثبات اتجاه عرض صحيح.
4. عند توفر قارئ شاشة مناسب: فحص ترتيب القراءة ونطق العربية والأعداد وعلامات الترقيم. إن لم يتوفر قارئ شاشة، سجّل «لم يُفحص» ولا «PASS».
5. حفظ اسم نظام التشغيل والطرفية ونسختها، الخط، locale, encoding، إصدار .NET، SHA, لقطة شاشة وفيديو أو سجل للنتيجة، وأي خلل مع خطوات إعادة إنتاج المشكلة.

## حدود القبول

لا تُغلق Stage49 بناءً على تشغيل آلي وحده. لا تُعلن `RTL visual PASS` أو `accessibility PASS` دون مشاهدة مستقلة في بيئة عرض حقيقية ودليل دائم. إذا فشل النص المرئي، سجّل بيئة الفشل وصوره وحدّد هل السبب هو الطرفية أو التطبيق قبل تعديل الإنتاج. لا يُفتح Stage50، ولا يُعدَّل `main` ولا يُدمج PR بهذه الخطوة.
