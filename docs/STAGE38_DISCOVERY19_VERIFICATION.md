This is semantically wrong because the Pastafarian date/year boundary changes with the calculation day; even the same year number (5000) may correspond to different opening and closing gates. Stage39 later preserves this bad key but adds three required guards: `calculationDayFingerprint`, `openGate`, `closeGate`. **Stage38 must not implement any of these guards.**

The stored value contains an immutable copy of the real Stage37 year record and the calculation day for forensic demonstration. Do not apply the Patch19 fix prematurely.

Every query physically invokes `patch18WalkYear`, including when it later encounters a bad HIT.
