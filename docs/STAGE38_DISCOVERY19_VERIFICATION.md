This is semantically wrong because the Pastafarian date/year boundary changes with the calculation day; even the same year number (5000) may correspond to different opening and closing gates. Stage39 later preserves this bad key but adds three required guards: `calculationDayFingerprint`, `openGate`, `closeGate`. **Stage38 must not implement any of these guards.**

The stored value contains an immutable copy of the real Stage37 year record and the calculation day for forensic demonstration. On HIT, the cached value is physically returned as `served`, including when it is stale. `staleCalculationDay`, `staleOpeningGate`, `staleClosingGate` and `oldWrongHit` are computed for *diagnostics only*; they DO NOT influence HIT or the returned value and are not guards. Do not apply the Patch19 fix prematurely.

Every query physically invokes `patch18WalkYear`, including when it later encounters a bad HIT. This entails the full authentic Stage37 signed-gate reconstruction, original Stage32 5781 and Stage33 5778 candidate predicates, old stable sort and Stage35 run-tie repair, real Seal10 year selection, real one-year-at-a-time Seal11/12 transitions as required, and both earlier old /365 diagnostic calls.
