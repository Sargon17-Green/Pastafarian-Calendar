## Causal construction

At source positions (180,7), (179,7), (178,7) the on-disk program
contains **three live traps `vvv`**. These source bytes are *not* the
instructions that a successful program should execute.

Earlier native self-modifications create non-constant, runtime-dependent
opcode bytes at gate sites (14,4), (63,4), (111,4). QA05 creates a
branch-dependent residue 1 or 2 at (9,9). These four values were previously
irrelevant *as data* to any postjoin instruction synthesis; now they are
compilation inputs. After joining at (320,7), the westbound common lane
executes an 88-instruction assembler at source columns (304..217,7),
which first reads these historically mutated gates and residue, then
computes and writes three new instructions into (180,7), (179,7), (178,7)
via native `p`. The assembler instructions are stored in reverse order
because the IP executes westward.

The generated instructions are:

`A = 48 + 10*((stamp + gate1 + gate2 + gate3) % 2)`

`B = 36 + (stamp-1)*(stamp-2)`

`C = 60 + (stamp-1)*(stamp-2)`

For genuine stamp=1 or stamp=2, the bytecode emitted at the traps is
either `0$<` or `:$<` (when read **from right to left**).
Both dialects have the same effect on the working data stack:
`0` pushes zero, `:` duplicates the top item; `$` pops that item;
`<` keeps the IP westward. The body of the future program is absent
from the original cells, and the exact branch-dependent A instruction
cannot be determined without evaluating the earlier memory history.

The two later history-dependent expressions are intentionally nonlinear:
altering the branch residue to 3 synthesizes B=38 (`&`) and C=62
(`>`), which no longer implement the same program. Changing an earlier
gate read may change the emitted A byte, or destroy the compiler.
In the final test, read/write timestamps and actual STEPs must establish
**older gate p → gate g → emitted opcode p → later executed opcode**.
It is not enough to compare numeric output, and an independent Python
emulation is not a substitute for PyFunge. Static `v` traps are negative
controls: after successful dynamic compilation their original source
bytes are overwritten before execution, so changing the disk text of
each trap should not alter the result.

## Native acceptance

Source blobs are SHA-pinned in the CI workflow. The harness compares
four valid and two invalid inputs with QA05 and production; valid ones
are checked against independent Befunge reference programs. It records
Native fork and join ticks, physical gate reads and writes, source-cell
overwrites, exact emitted opcode bytes, execution coordinates, stack depth,
and pointer continuation. Eight sabotage mutants target the upstream
branch history, gate readers and individual emitters, plus three
metamorphic controls where the original trap text is intentionally
changed but should be masked by runtime p.

The source is deterministic, so mathematical/static analysis can
in principle derive the generated bytes without literally running the
program; the claim here is **runtime-generated, input-history-sensitive
executable content**, not cryptographic uncomputability.

No Native PASS is asserted until the exact-head workflow succeeds.
Historical red attempts are retained for diagnosis.

## Native investigation: first-stage falsification (preserved)

Exact-head run 39033038919 (`f0717684`) proved four complete native
program constructions, two dialects (48,36,60) and (58,36,60), and
independent numeric parity across four valid and two invalid inputs.
Two branch-history corruption mutants caused bounded timeouts. The run
then failed on the `historical_gate1_read_removed` mutant because the old
acceptance rule expected altered final output or timeout. That is logically
insufficient: the runtime assembler can emit the *other equivalent dialect*
without changing the numeric output. The revised test now traces these
cases, compares the actual three emitted instruction bytes, and separately
reports a bytecode change and any output or termination change. The
original failed run is retained and is NOT called PASS.
